## 0.1.9 - 2026-11-24

- gatekeeper: `land <pr> --wait` on a PR in GitHub's merge queue, or queued for Mergify, waits until the queue merges it (exit 0) or takes it out, instead of exiting 0 once it is queued, which left a lead re-running `land` until the merge, each run re-reading the login, the permission, the rules and the merged high-risk PRs. Between rounds it reads only the PR's state, head, queue entry and labels, one GraphQL call a minute (two ETag reads on REST). A refused `gh api user` is kept for the process, and a REST read GitHub refused or rate-limited is not asked again within its round (#2101).
- `mergify.yml` sets `merge_conditions: [-conflict]` on the queue rule, so Mergify never checks a PR in place on its own branch (where the test step does not run): every merge goes through a draft PR (#2157). The header names the doc that says so; its comment on `max_checks_retries` no longer claims that setting keeps batches off the PR. A config test fails if in-place checks are allowed again. `tools/affected_tests.py` selects a package's whole test dir for a changed file under its `scripts/` or `src/` that no test names or ran.
- gatekeeper: a PR carrying `loop:hold` is refused at merge, by `land` and `check merge` alike, with `#<n> is held (loop:hold): see the hold comment on the PR`, so a bare `land` skips it and `land <n> --only` exits 1 without writing to it; `.mergify.yml` and its template take no PR carrying it, which lets a lead or another coordinator hold a PR it must not land (#2162).
- gatekeeper: a closing link to another repo's issue is no longer judged as the PR's own issue. `closing_issues()` keeps only GitHub's closing references into the PR's repo, as `closed()` does (the comparison is now `in_repo()`), so a PR body that closes a sibling repo's issue no longer fails `check merge` on that issue's missing spec record, nor passes on its approved one (#2165).
- gatekeeper: `land --wait` waits as long as the project's `land.wait` (a duration such as `2h` or `4h30m`; default 2 hours as before), so a project whose queue's checks run longer than 2 hours no longer has its land stopped while the PR is still being checked; the stop message names the configured time. A stop on a PR a merge queue holds, or whose checks run, leaves its `land` event `waiting` and writes no `needs-owner`; `needs-owner` stays for one nothing is moving. The landing lock's staleness stays 2 hours whatever `land.wait` is. `breakglass.max_age` shares the duration parser, so it also takes minutes and `1d12h` forms (#2172).
- gatekeeper: `approvals.py rerun-tests <failed-tests.json> --red <head> [--base <rev>]` is a red run's one rerun (R5): from the red run's failed test ids, its head and its base it recomputes the selection and runs loop.md's `Affected tests:` line against `<head>` when the change since the red reselects every failed test (the failed tests plus what the fix reaches), else against the base (the red run's whole selection, in its order); a failed test that passes there is named a flake, red again stays red, and one line says which case and why. Never the failed tests alone, and nothing is stored (#2177).
- gatekeeper: `select.unkeyed` in gatekeeper.md lists the checks whose pass is never reused, such as a step that reads a live service or the host itself. `local-ci`, `local-ci --record` and `reusable` always run such a step, and `no_pass` says why (#2180).
- gatekeeper: when the board refuses a `Low` risk, the line says the verifier's `Risk:` line alone shows the risk, instead of naming a `risk:high` label the PR doesn't carry (#2194).

## 0.1.8 - 2026-11-23

- gatekeeper: `check merge` runs loop.md's `pre_land` as `land` does (one shared run, `pre_land_run`), in a temporary worktree of the base's tip once nothing else holds the merge, so it never calls clear a PR `land` would refuse with "Refused by the pre-land check": a refusal prints `` `<cmd>` refuses it against <base> at <tip>, exiting <code>: land leaves it out `` with its output's end and exits 3 (a wait, since land keeps the PR ready), posting no comment. While something else holds the merge, or from a clone with no working tree, it prints `pre_land not run: <cmd>` instead (#2074).
- gatekeeper: `land.queue: github` is a valid policy value beside `mergify`. Where the base's ruleset requires a merge queue `land` hands PRs to GitHub's queue as before; where it requires none, `land` and `check stalled` refuse the setting and name the missing `merge_queue` rule, since `land` would otherwise merge each PR itself. `check stalled` now picks the queue in `land`'s order, so a base whose ruleset requires GitHub's queue is judged by it even under `queue: mergify` (#2091).
- gatekeeper: the GitHub adapter reads a PR's REST file list (`pulls/N/files`) once per run, forgetting it only after a write to GitHub or a wait's fresh read, so one brief on the REST path makes one call, not 30 to 60 (#2092).
- gatekeeper: `closes_nothing` no longer refuses a PR a `bot` section covers, such as a release workflow's own `cz bump` PR, whose `Part of` names a standing release epic that stays open across releases; an ordinary `Part of` PR, or the same PR with a person's commit on it, is still refused (#2103).

## 0.1.7 - 2026-11-23

- gatekeeper: `affected-tests` runs nothing when it can't tell what a change affects, says so in one line and exits 0, never the whole suite, which the nightly runs: a loop.md with no `Affected tests:` line, and a `--base` git can't resolve (the push of a new branch), no longer fall back to `mise run check`. Only the opt-out `Gate: full`, the project's own choice, still runs `check` (#1872).
- gatekeeper: a bump the gate proves mechanical (a pack bump whose `apm.yml` moves only the pack's `ref:` line, or a pin to a released pack tag) is no longer refused for naming no issue; any other PR, a `bot` section's other PRs and the release fold included, still needs its `Closes #<n>` (#2040).
- gatekeeper: a pack bump a cloud agent pushes to a `bot` section's `branch` gets the verifier-review exemption when its files are a released tag's byte for byte (`pin_target`), whoever its commits name, and a rename the tag makes no longer refuses it. The agent's `Claude <noreply@anthropic.com>` identity is the GitHub user `claude`'s, not no account, so its commits read as another account's push and the exemption never applied. A bump the tag doesn't prove keeps the commit-author check (#2059).

## 0.1.6 - 2026-11-23

- gatekeeper: a run answers a repeat of the same plain `gh api` read within 20 s from memory, emptied by any write, so one `approve merge` or `record verdict` no longer reads its PR three or four times (#2016).
- gatekeeper: under `land.queue: mergify`, a `land` success on a head counts as land's hand-over only when it is newer than land's last `Evicted from the merge queue` comment naming that head. A cloud eviction, whose `land: error` status is refused, left the old success newest, and Mergify labels `loop:dequeued` after every draft of a PR it held, so each re-land evicted the PR again and never handed it over. Now that label comes off as stale and the head is handed over again, in `land` and in `check stalled` (#2029).
- gatekeeper: a Mergify hand-over at a head `land` evicted before also comments `@mergifyio queue`, once per hand-over. Mergify does not take back a PR it dequeued for failing checks at an unchanged head through `.mergify.yml`'s `queue` action, only on that command (its merge-queue lifecycle docs; `requeue` is deprecated), so every such re-land was dropped and labelled `loop:dequeued` again (#2029).
- gatekeeper: `gate-record <head>` finds a gate step whose `paths` key it by its inputs as `local-ci` reuses one: by its inputs key on origin's record branches, on any tree, naming the tree and key the pass came from. It read such a step only on the head's tree, so a pass recorded on another tree with the same inputs read as no record and the verifier ran the step again. A step keyed by the tree keeps the tree match, and only origin's record branches count, as before (#2042).

## 0.1.5 - 2026-11-23

- gatekeeper: `loop.delegate_spec: false` restores owner-only specs and plans under `loop.delegate: all`: `approve spec|plan --by delegate` is refused, naming the key, and posts nothing; `check build` and `check merge` count no delegate's spec or plan record, with one line saying why; the delegate's go on a merge still counts. The key defaults to true, so a policy that doesn't set it keeps #1805's behaviour (#2018).
- gatekeeper: 0.1.5 is the first tag with #1872's no-gate `land` on a base with no merge queue, listed under 0.1.4 above, whose `gatekeeper-v0.1.4` tag predates it: read its upgrade note when moving from the 0.1.4 tag (#1872, #2026).

## 0.1.4 - 2026-11-23

- gatekeeper: `check stalled` judges every base, not only Mergify's: a PR `land` would take into a base it merges itself is listed while still open, and one into a base GitHub's merge queue holds while not in it; it also lists a PR whose newest verifier pass on its head is satisfied (or at the cap) but that still lacks its go or its `head_proof` record past `loop.stalled_after_hours` (default 4) since the later of its head's push and its newest verdict there, naming what is missing (`missing: go`); it reads the policy from the base and compares only the running code with the base's, so a worktree that edits or lags the policy files still judges; a PR it can't judge from this checkout (one stacked on another PR's branch, a base it can't fetch or whose policy is refused, a refused read) gets one `not judged` line, a last line counts them, and the rest are still judged (#1746).
- gatekeeper: under `loop.delegate: all`, `approve spec|plan <n> --by delegate` records the delegated approver's approval, under the owner's delegation, adds `approved:<point>` and lifts `needs-owner`; `check build` and `check merge` count it in place of the owner's record unless the PR touches `risk.critical_paths`. Without the setting it is refused. `approve breakglass` stays the owner's (#1805).
- gatekeeper: a `land --wait` that waits on a GitHub rate-limit reset resumes up to 3 minutes after it at random, not 1, so the lands that waited on one reset do not spend the fresh bucket in its first minute (#2000).
- gatekeeper: a cloud `land` after Mergify evicted a PR at an unchanged head posts a new `Queued for Mergify` record for the land-status workflow, rather than finding the old one and handing nothing over, since the eviction may have left `land: error` on that head (#2006).
- gatekeeper: behaviour change: on a base with no merge queue, `land` merges each landable PR on the verifier's record with no gate step. It runs no `loop.gate` or `gate_steps` command on the batch or on the base's new tip, reuses or asks for no recorded pass (a clone with no working tree no longer refuses a batch tree without one), publishes no `gate` status on main, and has no red-batch path left (no one-at-a-time retry, flake rerun, bare-base gate, eviction or `machine_exit` rerun); the `Landed` comment's `Gate:` line says `none at land, on the verifier's record of the head`. `check merge` waits only for the checks the base requires: a base that requires none waits for no aggregate `check` (fixes #349, where `check merge` held a PR `land` merged), and `ci: false` asks no `local-ci` pass. The verifier record, the owner's go and owner-only merges (`risk.critical_paths`, the levels), a `head_proof` and the base's required checks hold as before; the GitHub queue path is unchanged, and so is Mergify's hand-over but for one thing: on a Mergify base that requires no check, the hand-over at the end of `approve merge` and `record verdict` (which runs `check merge`) no longer waits for an aggregate `check`. Under `ci: false` an owner's break-glass still covers no required check, as before. The deprecated batch queue is gone: the `check queue` and `batch` verbs and the `Merge queue batch` proof. Upgrade note: `batch_queue` under `loop` and `land`'s `gate_on`, `cloud_gate_timeout_seconds` and `host_gate` now do nothing; a policy that still sets one parses, with one `ignored:` line on stderr naming it, so remove them at your next policy edit. `machine_exit` and `ci` still apply to `local-ci` (#1872).

## 0.1.3 - 2026-11-23

- Guidance: a known-red test gets a skip marker that links its issue, and the gatekeeper takes no expected-failures list.
- gatekeeper: `land --wait` asks GitHub only when what it waits on moved. Between two rounds it reads, every 30 s, only that: a land behind the landing lock reads the lock with one `git ls-remote` and makes no GitHub call until the lock moves past its holder's heartbeat (or stops beating for 15 minutes); a wait on a named PR's CI reads the base and the heads with one ls-remote and each head's check runs and statuses with an ETag (`If-None-Match`), which GitHub answers 304 at no quota while nothing changed, and runs the round again once a head, the base or a required check's state moved, or, for a land that left the free lock to an older waiter, that lock is freed, else after 15 minutes; it starts from what the round read, and a failed probe runs the round rather than ending the wait. The PR's `waiting` event and the land's place in the waiting order are still stamped every 5 minutes, by git push. `tests/test_land_wait_budget.py` counts the gh calls of one poll round of each wait state and fails above its budget (#1915).
- A cloud session's `land` with no merge queue merges over REST again. The proxy refuses `gh pr merge` as `non-200 OK status code: 403 Forbidden`, with no `HTTP 403`, which the GraphQL-refusal check now reads as a refusal; and the `land` status written just before the merge, which the proxy refuses, is now reported as not written instead of failing the land (#1917).

## 0.1.2 - 2026-11-22

- gatekeeper: `land: host_gate: false` makes `land` never run a gate on the host it runs on: a batch tree with no recorded pass, cloud or elsewhere, exits non-zero with `no cloud record for tree <t>` and starts nothing there, instead of falling back to a host gate (#1663).
- gatekeeper: `land --wait` spends less REST quota: `writer()` and `required_checks()` answers and a settled head's check runs are kept for up to 15 minutes (a head's commit statuses are still read every pass), the poll backs off from 300 s to 480 s while nothing changes, and `gh()` guards each call during the wait, waiting for the bucket's reset when fewer than 50 calls are left, or stopping with the reset time when that falls past the 2-hour ceiling (#1771).
- gatekeeper, upgrade note: a pack bump a cloud worker opens gets the `bot.<name>` fast path. Under a `branch` section a commit author with no GitHub account (a cloud worker's git identity) counts as the PR's author, as a committer with none already did; the head must still be this repository's own branch and every file match the section's `paths`. Such an exempt PR whose `apm.yml` changes only the `ref:` line of its `kzarzycki/agent-skills/engineering` dependency, to a release (a version, a range of one or the `engineering-v` tag, never a branch or a commit), the rest of the diff being the lock and generated files, needs no spec approval either; any other `apm.yml` change, and an exempt PR that leaves `apm.yml` alone (an updater's lock-only PR, a hand edit of a generated file), keeps the spec gate. A bump's branch is now `claude/ready-pack-bump-<tag>`, which a cloud session may push: before the next bump, change the policy's `bot.pack-bump.branch` from `pack-bump/` to `claude/ready-pack-bump-` and land it on the base, since the gatekeeper reads the policy from `origin/<base>` and the bump PR can't carry it; until then a `claude/ready-pack-bump-` bump goes through the full loop (#1800).
- gatekeeper: `approve merge` and a Mergify `land` work from a cloud session whose proxy refuses commit-status writes: the go's `Approved: merge` record, marked `Status: refused`, stands as the go on its head when written by a writer, and `land` hands over with `loop:queued` and a head-pinned `Queued for Mergify` record, which the new `land-status.yml` workflow turns into the `land` status (#1816).
- gatekeeper: the skill ships `mergify.yml`, the default Mergify queue for `land.queue: mergify`: a red batch is retried once, then split until only the failing PR leaves (`batch_max_failure_resolution_attempts: null`), and every batch runs on a draft PR from `mergify/merge-queue/`. A consumer copies it to `.mergify.yml` and gives its required check a step-level test `if` on that prefix, so a PR head runs only the cheap checks and each tree's tests run once, on its batch (#1821).
- gatekeeper: `approvals.py gate-record <head> [-- <command>]` says whether origin holds the gatekeeper's pass record of the gate (each `gate_steps` step), or of `<command>`, on the head's tree: exit 0 names the record branch, exit 1 names what has no record. A record is keyed by the tree and the command, so another tree or test list is never reused, and this clone's own record file never counts (#1822).

## 0.1.1 - 2026-11-22

- gatekeeper: `verdict` refuses an `Accepted on evidence:` phrase written inline in a `Manual:` line (a quote in prose, inline code or a fence takes nothing on evidence); verifier.md states the one-line form and the `Out of scope:` line, which blocks nothing (#1591).
- gatekeeper: `approve breakglass` and `breakglass-proof` record the owner's break-glass on one head with a red or missing required check, and `check merge` stops holding on that check while the record is current (#1722, part 1: the run-data proof and the refusals follow).
- gatekeeper: land verifies the break-glass proof from GitHub's run data (the failure on the head, its failed tests classified against main's runs, a re-run alone, a smoke run, earlier green runs) and leaves a verified PR unmerged for the owner's UI merge; `qualify` publishes the failed test ids as the `failed-tests` artifact and takes a `tests` input for the re-run (#1722, part 2).
- gatekeeper: no helper merges past the base's rules: `gh()` refuses the bypass flag and any REST merge field but the merge's own, the adapter's `merge` and `land` refuse any merge while a required check is red, pending or missing on the head, and a test asserts no script of the pack holds the bypass flag (#1722, part 3).
- gatekeeper: under `land.queue: mergify`, `approve merge` and `record verdict` each end by queueing the PR when `check merge` passes, and print what is missing otherwise; `check stalled` lists every open PR that has its go and a satisfied verdict but is neither queued nor merged (#1741).
- gatekeeper: behaviour change: session links now stay in squash bodies, PR bodies and comments. `land` merges with GitHub's default squash body (no `--body`, no REST `commit_message`) and edits no PR body or comment before a merge, an enqueue or a Mergify hand-over; `check merge` no longer names a text holding a session link, and the `commit-msg` verb is gone, so drop any hook that runs it (#1764).
- gatekeeper: a test pins that two successive merges of the base carry the old head's verdict (#1768).

## 0.1.0 - 2026-11-22

- gatekeeper: the first release, split out of `engineering`. The `gatekeeper` skill holds `scripts/gatekeeper.py`, its GitHub adapter `scripts/github_adapter.py` and the `scripts/approvals.py` shim, with their tests; it depends on no other package. `brief` and `release` leave it for the loop's own `scripts/loop.py` (#615).
- gatekeeper: a team that installs only the gatekeeper finds the policy it reads in this skill. `policy.md` holds every policy key with its type, default and an example block, and issue-tracker.md's settings block, which the loop's SKILL.md § Settings held; the gate's rules stay in the loop's SKILL.md § Approvals and proof. The helpers it loads from beside itself (`acceptance.py`, `events.py`, `folding.py`) and `events.md` move with it, and the omnigent-agents skill's driver is found by the host's install layout. Its references to the loop's role files no longer name them by file (#615).
- gatekeeper: a cloud session on a base without the merge queue and without `land.signed_squash_to` now lands over REST (`PUT pulls/N/merge`, squash, `sha` the gated head), which GitHub signs, so it needs no signing key; the adapter's `merge` takes this route whenever GitHub refuses GraphQL. A land that asks for `signed_squash_to` with no `ssh-keygen` installed is refused with that reason instead of a `FileNotFoundError` (#1712).
