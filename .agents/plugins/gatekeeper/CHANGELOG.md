## 0.1.16 - 2026-11-25

- A `gate_steps` step may set `on_demand: true`: `local-ci` and `local-ci --record` skip it, saying so in one line, `land` never needs it, and a `gate_steps` with every step on demand is refused; `local-ci --record --step <name>` runs only the named steps and records, publishes and reuses each pass by its inputs key, writing no `gate` status (#2295).
- gatekeeper: a claim names the Omnigent session that holds the issue (#2324). Under Omnigent, `check build`'s `Assigned:` record adds `Session: <server>/c/<lead's session id>` (the lead's, also when a worker or verifier runs it) and the issue's `Session` issue field is set to the same link with `setIssueFieldValue`. The field is optional and the account's owner creates it: without it, or where GitHub refuses GraphQL, the run makes one lookup and prints one line, and the claim, the record and the exit code are as before; a refused write is one line. Outside Omnigent nothing changes. Where GitHub refuses GraphQL, the field is set over REST (`POST .../issues/<n>/issue-field-values`), with its id read off an issue already carrying a value. `check setup` reports a missing `Session` field in one line with the steps to create it on GitHub, and exits as before.
- queue-select prints the floor for a project with no `Affected tests:` line (the `select` cut, then the full check), so a batch never merges a PR with no record untested; the refusal for an empty selection stays as a guard (#2362).
- `check build` and `check merge` no longer record a delegate's `approved:spec` label (added under the owner's login) as the owner's approval; an issue with the delegate's current record is left alone (#2430).
- gatekeeper: `timeouts.run` stays the one gate budget, and a selection over it fails fast (#2445). `timeouts --check` now also names, one line each, a marked workflow job's `timeout-minutes` (`# timeouts.run` after it), the variable loop.md's `Wall-clock variable:` names, a hand-set `land.wait`, and a nightly workflow (`# timeouts: nightly`) whose push paths differ from `select.build_inputs`. `durations --record` turns the nightly's JUnit XML or `--durations=0` output into the durations file `shards --durations` reads. `affected-tests` estimates a whole-suite run (recorded seconds over `GATE_WORKERS`, plus `GATE_SETUP_SECONDS`; per shard under `select.shards`) and exits 124 in one line when it is over 80% of `timeouts.run`; with no recorded durations it says so and runs. Each run records its estimate beside its actual time, and `durations --report` flags drift over 25%. New `select.build_inputs_in_queue: floor | full` (default `floor`): in the merge queue a build input selects the other changed files' tests plus, for `uv.lock`, the tests that import a package whose version moved, and the run after merge covers the rest.

## 0.1.14 - 2026-11-24

- gatekeeper: breakglass.md names the re-run of the proof by what it runs, `approvals.py rerun-tests` on the failed ids (the red run's whole selection, R5), never the failed ids alone; this repo's `qualify` calls it on a rerun attempt of a red batch run and on a `tests` dispatch (#1794).
- `approvals.py land` starts the omnigent-agents skill's `omnigent_agent.py own-pr <owner/name#N>` detached for each PR it names, so a merge-queue dequeue of a PR a lead lands, or took over, reaches that lead (#2161).
- gatekeeper: `affected-tests` runs the narrowest set it can name where it can't tell exactly, instead of nothing: a `--base` git can't resolve (the all-zeros SHA of a new branch) selects against the merge base with the branch's base, and a loop.md with no `Affected tests:` line runs gatekeeper.md's `select` cut, then `mise run check` for a change the cut can't settle. Zero runs only for a change of non-product paths, saying `0 selected: non-product`. - gatekeeper: `select.shards: <n>` in gatekeeper.md splits a whole-suite selection into `n` disjoint shards balanced by the last full run's durations (`approvals.py shards`, never more shards than items); a CI job records a shard's pass with `shards --record <head> --shard <i> --command <cmd>`, R1's record keyed by the tree and the shard's command, and the run passes when `shards --passed` finds every shard's. Off by default; a narrow selection is never split (#2229).
- gatekeeper: `scripts/loop_metrics.py` (`loop-metrics <owner/repo>... --since <date>`) prints one read-only line per repo for the week: merged PRs, median ready->merged time, runner-minutes per merged PR (a queue batch's minutes split evenly), reverts and red nights, and the week before beside them. `merged with no record` prints `not measured yet (#2310)`: a record ref is deleted at landing (#2233).
- gatekeeper: each `levels` entry takes `rerun` (default `false` for `low`, `true` for `high` and `critical`). With it on, `check merge` and `land` refuse a head whose only proof is the worker's record: they wait for an independent rerun of its selection on its tree, a `local-ci --record --rerun` record that an app pushed (a CI run) or that a verifier pass on the head names on a `Rerun: <commit>` line. `local-ci --record --rerun` reruns the selection reusing no pass and keys its record apart from the worker's. `check rerun <pr>` says whether a head needs a rerun, and `--no-push` keeps the rerun's record as a local branch for a CI job without a write token; this repo's `rerun.yml` runs the selection with a read-only token and pushes the record from a second job that runs none of the PR's code `verdict` carries the report's `Rerun:` line into the review, and `report` warns on a high-risk report naming none where there is no CI; a head of the same tree keeps the rerun its carried verdict named; `check rerun` says `not needed` wherever `check merge` asks no verifier pass; only the account `loop.rerun_pusher` names (default `github-actions[bot]`) counts as the CI's push `check rerun` writes nothing: it reads the owner's approval labels as `check merge` would record them, without recording them (policy.md, Independent rerun) (#2240).
- gatekeeper: a second queue timeout at the same head stops requeueing (#2308). The PR stays out of the queue with one line naming `timeouts.run` and its length, and `land` exits 3 as a wait on a person: raise the budget or shard the suite. The first timeout still requeues. GitHub's queue counts the head's timeout removals from its own timeline (`checks_timed_out`, or `failed_checks` whose required checks only timed out); Mergify's from the `Timed out in the merge queue` record land comments at the first, then a `Timed out twice in the merge queue` record, which a new head, a ready-again or a changed `timeouts.run` lifts; the GitHub queue leaves the same record at its stop, so its stop lifts the same ways. A Mergify stop that lifts asks Mergify to queue the head again (`@mergifyio queue`, as after an eviction), and a second timeout counts only when the timed-out queue check finished after the first record.
- `check build` and `check merge` say why a row line or `spec:paths` left a spec to the owner only while the owner's approval is missing; with the approval recorded, those lines no longer refuse the PR (#2392).

## 0.1.13 - 2026-11-24

- gatekeeper: gatekeeper.md's `select` (`build_inputs`, optional `checks`) cuts `affected-tests` and the narrowed gate (`local-ci --record`, with or without `--base`, and `local-ci <pr>` under `ci: false`) by build input: a change whose every file is non-product (docs, prose, `.agents/`, `.claude/`, the pack's `apm.yml` and lock, or a check's paths) skips the `Affected tests:` command and runs only the checks it touches, so a docs, skills or pack-bump PR skips the build and the suites; a moved file counts under both its names, and a path matching neither list and the policy files count as build inputs, and a project whose tests read a file under `docs/`, `.claude/`, `.agents/` or any `.md` lists it in `build_inputs`; the change is the head's commits since the base (`local-ci <pr>`, `land` and the merge queue read the PR's head from any checkout), and uncommitted or untracked changes, a diff git can't list, or `select` without `build_inputs` cut nothing; a narrowed record of a non-product change is keyed by the checks it ran, and `gate-record`, `land` and the merge queue find it (#1638).
- gatekeeper: one `timeouts` block in gatekeeper.md (`test: 60s`, `run: 60m` by default, today's values) sets every time limit of a run, so raising one moves the others: the Mergify queue's `checks_timeout` (`approvals.py queue-config`, and `gatekeeper.py timeouts --mergify`, render it into `.mergify.yml`, `timeouts --check` and `check setup` say when the file is out of step), a CI job's `timeout-minutes` (printed by `gatekeeper.py timeouts` for the templates that render workflows) and `land --wait`'s ceiling, the queue's checks timeout plus one more run (2 hours with nothing set, 8 hours with `run: 4h`). `land.wait` is deprecated: a set value still overrides the ceiling, with a `deprecated:` line. The landing lock's staleness stays 2 hours. A malformed duration is refused, naming the key. `affected-tests` stops a run still going at `timeouts.run` and exits 124 with one line naming the budget, the selection's size where it knows it (the whole suite under `Gate: full`; else unknown, with the count of changed files) and that it ran unsharded. A timeout is never a test's failure: a GitHub merge queue removal whose required checks only timed out counts for nothing, and a Mergify dequeue its check run calls a timeout is queued again instead of evicted (#2228).

## 0.1.9 - 2026-11-24

- gatekeeper: `land <pr> --wait` on a PR in GitHub's merge queue, or queued for Mergify, waits until the queue merges it (exit 0) or takes it out, instead of exiting 0 once it is queued, which left a lead re-running `land` until the merge, each run re-reading the login, the permission, the rules and the merged high-risk PRs. Between rounds it reads only the PR's state, head, queue entry and labels, one GraphQL call a minute (two ETag reads on REST). A refused `gh api user` is kept for the process, and a REST read GitHub refused or rate-limited is not asked again within its round (#2101).

- gatekeeper: a closing link to another repo's issue is no longer judged as the PR's own issue. `closing_issues()` keeps only GitHub's closing references into the PR's repo, as `closed()` does (the comparison is now `in_repo()`), so a PR body that closes a sibling repo's issue no longer fails `check merge` on that issue's missing spec record, nor passes on its approved one (#2165).
- gatekeeper: `land --wait` waits as long as the project's `land.wait` (a duration such as `2h` or `4h30m`; default 2 hours as before), so a project whose queue's checks run longer than 2 hours no longer has its land stopped while the PR is still being checked; the stop message names the configured time. The landing lock's staleness stays 2 hours whatever `land.wait` is. `breakglass.max_age` shares the duration parser, so it also takes minutes and `1d12h` forms (#2172).
- gatekeeper: `approvals.py rerun-tests <failed-tests.json> --red <head> [--base <rev>]` is a red run's one rerun (R5): from the red run's failed test ids, its head and its base it recomputes the selection and runs loop.md's `Affected tests:` line against `<head>` when the change since the red reselects every failed test (the failed tests plus what the fix reaches), else against the base (the red run's whole selection, in its order); a failed test that passes there is named a flake, red again stays red, and one line says which case and why. Never the failed tests alone, and nothing is stored (#2177).
- gatekeeper: `select.unkeyed` in gatekeeper.md lists the checks whose pass is never reused, such as a step that reads a live service or the host itself. `local-ci`, `local-ci --record` and `reusable` always run such a step, and `no_pass` says why (#2180).
- gatekeeper: when the board refuses a `Low` risk, the line says the verifier's `Risk:` line alone shows the risk, instead of naming a `risk:high` label the PR doesn't carry (#2194).

A bump's branch is now `claude/ready-pack-bump-<tag>`, which a cloud session may push: before the next bump, change the policy's `bot.pack-bump.branch` from `pack-bump/` to `claude/ready-pack-bump-` and land it on the base, since the gatekeeper reads the policy from `origin/<base>` and the bump PR can't carry it; until then a `claude/ready-pack-bump-` bump goes through the full loop (#1800).

A consumer copies it to `.mergify.yml` and gives its required check a step-level test `if` on that prefix, so a PR head runs only the cheap checks and each tree's tests run once, on its batch (#1821).
- gatekeeper: `approvals.py gate-record <head> [-- <command>]` says whether origin holds the gatekeeper's pass record of the gate (each `gate_steps` step), or of `<command>`, on the head's tree: exit 0 names the record branch, exit 1 names what has no record. A record is keyed by the tree and the command, so another tree or test list is never reused, and this clone's own record file never counts (#1822).
